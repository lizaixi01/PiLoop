# v0.1.4 首次交付对照实验

2026-09-11。**没有证明新增验证约定提高首次交付通过率。**

## 预先固定的方案

- 3 类任务：带回绕/复位的计数器、一位 mux、组合搜索/库存筛选；每个任务每组重复两次，共 12 次独立模型会话。
- DeepSeek / deepseek-flash，thinking=low；同一模型配置，未设置随机种子或显式温度。
- 两组都有相同的默认工具与 verify_web_page，仅对照组去掉两段新增运行验证约定。因此这是**提示约定的消融实验，不是原版 Pi 与整个 PiLoop 的产品对比**。
- 每次 150 秒、最多 24 次工具启动；网页工具每次用户输入最多 3 次。超时或未正常结束计失败，不能仅凭留下正确文件计成功。
- 每次相同初始 HTML、独立项目与会话，没有人工追问或中途修改规则。第二轮颠倒组别顺序。
- 验收步骤由实验宿主在模型运行前固定，运行后检查两种视口；不向模型提示验收脚本。文件位于项目外，但没有 OS 级隔离，不能声称绝对不可访问。
- 协议 SHA-256：`a43b6bc608b7e65d17e443ce49f2007c20f8bfadea59a3385dd61d75c6844d17`。脚本：`scripts/web-delivery-eval.mjs`；原始协议、会话、截图及结果保存在本地忽略目录 `.piloop-eval-release014/`，不发布账号或原始会话。

## 失败归因

counter-0-verification 修复了代码，首次普通操作检查通过。之后模型为边界补充检查，把点击次数与预期值配错，工具如实返回断言失败。模型又重复检查、尝试绕到 bash 调查，最终触发时间预算。宿主独立检查相同最终文件通过。

可观察的近因是模型生成的测试方案错误；Harness 新约定没有可靠避免重复错误验证，三次限制也只管本工具，不管 bash。不能把全部责任简单归为模型或测试工具，也不能删除这次失败来制造收益。

## 发布决策

发布可复现的工具、记忆和启动改进；不宣称一击命中率已提高。下一轮优先研究如何区分实现错误与验收方案错误，并在无新证据时停止重复验证。不能用同一批已见任务反复调提示词后当作未见测试成绩。
